Motivation

Why Systematic Bring-Up Validation?

🔍

Silent Failures

PCIe replay errors, HBM ECC faults, and clock throttling cause non-deterministic training divergence and inference errors that are invisible without targeted tests.

📊

Performance Regression

A single misconfigured NUMA binding or power cap can reduce AI throughput by 30–50%. KPIs capture measurable baselines before and after every change.

✅

Production Readiness

Workload acceptance gates (inference latency, training throughput, KV cache) confirm the node is ready for production SLAs before serving traffic.

⚡

Hardware Defect Detection

ECC uncorrected errors, retired HBM pages, and PCIe link replays surface early hardware faults that would otherwise manifest as random crashes.

🔁

CI/CD Regression Gate

Every driver update, framework upgrade, or config change is validated against the same KPI thresholds, preventing silent regressions.

📝

Audit Trail

Auto-generated TESTCASE_EXECUTION_FINAL_REPORT.md gives a time-stamped, human-readable record of every test run for compliance and handover.

CPU Focus · Host CPU in a CPU+GPU Node

Host CPU — Priority KPIs in a CPU+GPU AI System

The Host CPU performs orchestration, preprocessing, I/O, NUMA-aware memory staging, and torch.compile. A CPU bottleneck stalls all 4 GPUs simultaneously without appearing in GPU utilisation metrics.

🔴 CRITICAL — CPU Bottleneck Stalls All GPUs
  • overlap_pct ≥ 60% — CPU prefetch/GPU compute overlap; GPU idle = direct revenue loss
  • tokens/s ≥ 200k — CPU tokenizer must outpace GPU decoder throughput
  • scaling_ratio ≥ 2× — multi-thread tokenizer (1→4 threads); broken threading visible here
  • h2d_bw ≥ 41 GB/s — CPU-initiated PCIe H2D for weight & data loading
  • kernel_launch p50 < 10 µs — CPU→GPU dispatch latency per batch step
  • seq_read GB/s — CPU I/O subsystem for 140+ GB model weight files (NVMe)
  • dram_bw ≥ 75% DDR5 — CPU data-staging bandwidth between DRAM and GPU
🟡 HIGH — CPU Performance Affects SLA
  • NUMA local > remote BW — wrong NUMA binding adds ~20% latency (GPU PCIe affinity)
  • cpu_fp32_gflops ≥ 70% — attention masks, post-processing, CPU-side decode steps
  • parallel_speedup ≥ 0.85 — threading efficiency of parallel preprocessing pipeline
  • kv_eff ≥ 80% — CPU-managed KV cache HBM allocation efficiency
  • ar_overhead % — CPU-orchestrated NCCL AllReduce scheduling overhead per step
  • speedup_ratio ≥ 1.05× — torch.compile Inductor/Triton runs on CPU; if <1× it adds latency for zero gain
🟢 IMPORTANT — Correctness & Reliability
  • allreduce_err < 1e-3 — CPU coordinates NCCL gradient sync; silent error = wrong model convergence
  • callback_executed = True — host-side CPU stream callbacks must fire after GPU work
  • concurrent_ratio ≤ 1.5× — CPU CUDA driver scheduling 4 streams concurrently
  • sync_overhead p95 < 1ms — CPU cudaStreamSynchronize() cost accumulated per training step
  • tcp_bw Gbps — CPU network stack for gradient exchange & checkpoint transfer

Key insight: Every GPU kernel is dispatched by a CPU thread. If the CPU is slow, misconfigured (NUMA), or thermally throttled, all 4 GPUs are underutilized — even if per-GPU compute metrics look healthy.

Why It Matters

The CPU preprocessing pipeline (tokenization, padding, batching) must feed GPUs faster than they consume data. A bottleneck here causes GPU idle time that does not appear in GPU utilization metrics alone.

Domain E · System Health & Reliability

GPU Thermal & Clock Stability

Why It Matters

Each GPU has a model-specific thermal limit. When this limit is approached, hardware reduces SM clock frequency to stay within thermal/power budget. This is transparent to users but directly reduces compute throughput. Long-running training jobs may degrade by 10–30% without explicit runtime errors.

Test Cases (4)

  • Idle temperature below detected max operating temperature
  • Clock boost ratio ≥ 80% of advertised max
  • SM clock drop ≤ 10% during 30s sustained GEMM
  • Power draw ≤ 90% of programmed power limit at rest

KPIs Generated

temperature_c
Per-GPU temperature (°C) — threshold from detected spec
clock_ratio
current_clock / max_clock (threshold ≥ 0.80)
clock_drop_ratio
SM clock drop during sustained load (≤ 0.10)
power_ratio
Idle power / power limit (≤ 0.90)

Domain F · System Health & Reliability

GPU ECC & PCIe Link Health

Why It Matters

A single uncorrected ECC error (UE/DBE) in accelerator memory can silently corrupt tensor values, causing model training to diverge or inference to produce wrong outputs. PCIe replay counters indicate signal integrity failures that manifest as random slowdowns and data corruption.

Test Cases (4)

  • VRAM/HBM uncorrected ECC count = 0 (per GPU)
  • VRAM/HBM corrected SBE count < 100 (per GPU)
  • PCIe link replay counters = 0 (all GPUs)
  • Retired memory pages (DBE) < 10 per GPU

KPIs Generated

ue_count
Uncorrected ECC errors — must be 0
ce_count
Corrected SBE count — threshold < 100
pcie_replays
PCIe replay counter per GPU — must be 0
retired_pages
Retired memory pages (DBE) — threshold < 10

Domain G · System Health & Reliability

Energy Efficiency (GFLOPS/W)

Why It Matters

Total Cost of Ownership for AI clusters is dominated by power. The suite compares measured TFLOPS/W against each GPU's detected theoretical peak. A value far below expectation reveals power capping, thermal derating, or underutilized compute — all of which inflate operating costs per token served.

Test Cases (2)

  • Per-GPU FP16 TFLOPS/W ≥ 1.0 (runs sustained GEMM, samples power in parallel)
  • Aggregate 4-GPU FP16 TFLOPS/W ≥ 1.0 (concurrent GEMM on all GPUs)

Examples: H100 SXM5 ≈ 2.83 TFLOPS/W, H100 PCIe ≈ 4.32 TFLOPS/W, MI300X ≈ 1.74 TFLOPS/W theoretical FP16. Floor of 1.0 allows for thermal and power derating.

KPIs Generated

fp16_tflops
Measured FP16 TFLOPS (sustained GEMM)
mean_power_w
Average GPU power draw during benchmark (W)
tflops_per_watt
FP16 efficiency (threshold ≥ 1.0)
total_power_w
Aggregate system GPU power (4-GPU test)

Domain I · System Health & Reliability

Multi-GPU Gradient Synchronization Correctness CPU Primary

Why It Matters

DDP training correctness depends entirely on NCCL producing the exact arithmetic mean of gradients across all ranks. A hardware or NCCL bug that produces silently wrong allreduce results causes models to converge to wrong minima — an extremely hard-to-diagnose failure mode.

Test Cases (3)

  • NCCL allreduce(MEAN) matches CPU-computed reference (max abs error < 1e-3)
  • Single-GPU gradient computation self-consistency
  • Multi-GPU tensor PCIe/fabric copy bit-identity

allreduce_err

grad_rel_err
Gradient computation max relative error
tensor_max_diff
PCIe/fabric copy bit-identity difference (must be 0.0)

Domain J · System Health & Reliability

torch.compile() Correctness & Speedup CPU Primary

Why It Matters

PyTorch 2.x torch.compile() with Inductor/Triton generates custom kernels at runtime. Bugs in kernel generation can produce numerically wrong outputs without raising exceptions. Additionally, if compilation does not deliver speedup on the target platform, enabling it adds latency overhead for no gain.

Test Cases (2)

  • Compiled FP16 linear model output matches eager output (max abs error < 1e-2)
  • Compiled GEMM block is ≥ 1.05× faster than eager after warm-up

Domain K · System Health & Reliability

CUDA Stream Ordering & Sync Correctness

Why It Matters

vLLM, FlashAttention, and custom CUDA operators use multiple streams with event barriers for correctness. A broken event ordering gives the GPU permission to execute a consumer kernel before the producer finishes — causing data races that produce wrong results intermittently, often only under high load.

Test Cases (5)

  • Event wait enforces producer → consumer ordering
  • No race condition on shared tensor across two streams
  • CUDA event elapsed time is positive and plausible
  • Stream callback executes on host after GPU work
  • 4 concurrent streams complete in < 1.5× serial time

KPIs Generated

ordering_correct
Event barrier enforces correct execution order (bool)
gemm_elapsed_ms
CUDA event timing sanity check
concurrent_ratio
Concurrent / sequential time (threshold ≤ 1.5)
callback_executed
Host callback fired after synchronize (bool)

Node Validation & Bottleneck Analysis

Node Validation (TC-NV-01 → 08)

  • GPU enumeration & PCIe topology — all detected accelerators correctly wired
  • PCIe H2D/D2H bandwidth — ≥ 65% of 63 GB/s Gen5 theoretical
  • Pinned vs pageable memory — DMA engine performance
  • P2P bandwidth — all GPU pairs via PCIe fabric
  • Kernel launch & sync latency — p50 < 10 µs
  • Power stability — variance < 50W under workload
  • NCCL init & allreduce — collective health check
  • Workload acceptance — GPT-2, BERT, Llama 7B inference + training

Bottleneck / Roofline Analysis (TC-BN-01 → 06)

  • CPU FP32 efficiency — measured vs SIMD theoretical (target ≥ 70%)
  • CPU DRAM bandwidth — STREAM Triad ≥ 75% of DDR5 peak
  • GPU FP16 efficiency — per-GPU & aggregate vs detected peak (target ≥ 75%)
  • Accelerator memory bandwidth — ≥ 80% of detected theoretical peak
  • PCIe bottleneck — identifies compute vs memory vs interconnect bottleneck
  • Scaling efficiency — multi-GPU linear speedup ratio

Platform caveat: P2P bandwidth depends on NVLink/xGMI availability; PCIe-only systems show lower peer bandwidth. Compute-efficiency thresholds use percentage-of-peak to keep cross-platform comparisons fair.

KPI Framework

How KPIs Help: From Raw Numbers to Decisions

1. Threshold-Based Pass/Fail

Every KPI has a quantified threshold tied to hardware specs. A test passes only when the measured value crosses the threshold — this converts subjective "looks OK" to an objective gate.

2. Regression Detection

KPIs are persisted to JSONL files with timestamps. Running the suite after a driver update immediately surfaces whether, e.g., tokenizer throughput dropped 15% or TTFT regressed.

3. Root-Cause Triage

Correlated KPIs pinpoint the bottleneck layer: if tflops_per_watt is low but fp16_tflops is normal → power cap. If TTFT is high but prefill_tflops is normal → data loading is the culprit.

4. Automated Report Generation

Each pytest session auto-generates TESTCASE_EXECUTION_FINAL_REPORT.md with color-coded pass/fail/skip tables and inline KPI values — ready for stakeholder handover without manual editing.

5. Comparative Benchmarking

KPIs enable A/B comparison: node A vs node B, pre- vs post-driver-upgrade, or PCIe Gen4 vs Gen5. Numeric evidence replaces subjective assessment.

6. Platform Recalibration

When thresholds fail on any platform, KPI values show the exact baseline gap and whether the issue is compute, memory, interconnect, or orchestration related, enabling targeted threshold recalibration instead of blanket waivers.

KPI Framework · CPU Focus

Decision Scorecard: KPIs That Matter Most

Simplified operator view: track the smallest KPI set that drives deployment decisions and fastest triage.

Deployment Gate KPIs (P0/P1)

  • P0TTFT / ITL — user-facing latency SLA must hold under realistic batch and context lengths.
  • P0FP16/BF16 % of peak — confirms accelerator compute utilization is competitive.
  • P0mem_bw_tbps % peak — validates memory subsystem is not the hidden bottleneck.
  • P1CPU overlap_pct + tokens/s — detects host-side feeding bottlenecks that idle all GPUs.
  • P1h2d_bw_gbps — verifies PCIe transfer path for weights and batches.
  • P1tool_parallel_speedup — validates agentic multi-tool execution scales as expected.

Fast Triage Map

  • ComputeLow TFLOPS with normal memory BW: kernel shape, occupancy, or power cap issue.
  • MemoryLow memory BW with healthy clocks: ECC overhead, NUMA placement, or workload access pattern.
  • InterconnectLow H2D/D2H or P2P BW: PCIe generation/width mismatch or topology constraints.
  • CPU HostLow overlap_pct / tokenizer throughput: data pipeline or thread-affinity bottleneck.
  • ReliabilityAny UE ECC or high replay count: hardware integrity action before workload sign-off.

Recommended cadence: run full KPI suite weekly, run P0/P1 scorecard on every driver/framework change, and block rollout on any P0 regression.
