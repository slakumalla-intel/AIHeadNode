Test Name

Host CPU, Memory and PCIe Peripheral Path Validation

This system-level test measures CPU submission and wait behavior, pinned host-memory allocation, host-device transfers across the PCIe path, bidirectional peripheral traffic, CPU scheduling, and the effect of 2 MB hugepages. The GPU is treated as the PCIe endpoint used to exercise the host path, not as the primary subject of the test.

Description

The validation combines two focused workloads captured with NVIDIA Nsight Systems:

WorkloadPurposeCapture
CPU submission and wait behaviorMeasure CPU-side CUDA launch calls, synchronization waits, host allocation, and 1 MB host-peripheral round-trip latency.cpu_gpu_launch_sync.nsys-rep
PCIe and host-memory peripheral pathMeasure direct H2D/D2H bandwidth, copy-engine and SM-assisted transfers, bidirectional traffic, pinned memory, CPU scheduling, and hugepage behavior.pcie_memory_latency.nsys-rep and cpu_pcie_memory_latency.nsys-rep

Procedure

  1. Confirm the host CPU topology, NUMA layout, PCIe topology, driver/runtime versions, peripheral inventory, and idle system state.
  2. Activate the project virtual environment and use one logical endpoint with CUDA_VISIBLE_DEVICES=0 to keep the host-path comparison controlled.
  3. Run the CPU submission and synchronization workload under Nsight Systems with OS runtime tracing.
  4. Run the PCIe and host-memory tests selected by the pcie_validation and memory_validation markers, including a run with CPU context-switch tracing.
  5. Export each .nsys-rep file to SQLite and review CPU waits, host allocations, copy API calls, transfer-engine activity, and PCIe traffic.
  6. Compare per-call latency and bandwidth with thresholds; keep aggregate allocation and transfer time separate from endpoint latency.

Test Method

Nsight Systems traced CUDA API calls, peripheral transfer operations, operating-system runtime calls, CPU process samples, and CPU context switches. GPU kernel records are retained only to identify time spent by the endpoint while the host is waiting. The primary report names supported by Nsight Systems 2025.6.3 were used:

cuda_api_sum, cuda_gpu_kern_sum, cuda_gpu_mem_time_sum, and cuda_gpu_mem_size_sum.

Latency values reported by the Python test are measured in microseconds. Transfer bandwidth values are reported in GB/s by the validation code and by nvbandwidth. Nsight aggregate times include all calls in the capture and therefore are not equivalent to the latency of one API call.

Performance Improvement Opportunities

PriorityActionReason from this captureExpected effect
1Reuse pinned host buffers instead of allocating and freeing them for each transfer.cudaHostAlloc and host allocation APIs dominate aggregate CPU/API time.Reduces CPU setup cost and removes allocation-related stalls.
2Batch small transfers and use persistent cudaMemcpyAsync operations on dedicated streams.Small transfers pay fixed launch and synchronization costs; the trace contains hundreds of copy operations.Improves effective PCIe bandwidth and lowers per-transfer CPU overhead.
3Replace broad stream/device waits with event-based waits for only the required buffer.Stream synchronization totals include time waiting for outstanding transfer and endpoint work.Allows CPU work and independent transfers to overlap with peripheral activity.
4Pin the transfer thread to a CPU close to the PCIe root complex and bind memory to the matching NUMA node.CPU scheduling and NUMA placement are host-side controls that directly affect DMA preparation and submission.Reduces host staging and submission variability; validate with numactl and CPU affinity comparisons.
5Keep 2 MB hugepages enabled for the intended buffer path and compare with a controlled non-hugepage run.The capture reports hugepages active and shows approximately 55.9 GB/s H2D and 55.3 GB/s D2H copy-engine bandwidth.Can reduce host page-management overhead; retain only if repeatable under the production buffer size.
6Use a warm-up phase and steady-state measurement window before collecting production KPIs.Initialization, library loading, allocation, and first-use costs inflate aggregate totals.Produces more stable CPU/peripheral latency baselines.
Recommended next experiment: run the same transfer workload with reusable pinned buffers, NUMA/CPU affinity, and batched asynchronous copies. Compare p50/p95 host wait time, H2D/D2H bandwidth, allocation count, and the number of synchronization calls against this baseline.

Conclusion

From a system perspective, the host CPU, pinned-memory path, PCIe transfer path, copy engines, bidirectional traffic, and hugepage configuration met the measured acceptance thresholds.

The main optimization target is host-side overhead rather than GPU compute: pinned-memory allocation, stream waits, CPU scheduling, NUMA placement, and the number and size of transfers. Aggregate synchronization totals include outstanding peripheral and endpoint work and must not be reported as single-call CPU latency.

The baseline is suitable for comparison. The NUMA-bound repeat confirms stable H2D performance at 56.18 GB/s direct and 56.29 GB/s copy-engine bandwidth. NCU adds endpoint-kernel diagnostics, while the host optimization focus remains pinned-buffer reuse, transfer batching, reduced broad synchronization, and repeatable CPU placement.
