Executive Summary

All four successful runs finished with 24 passed, 1 failed. The only repeated hard failure was TestNVLinkBottleneck::test_nvlink_bw_vs_theoretical, with measured NVLink bandwidth tightly clustered around 264.3 to 264.5 GB/s, or about 29.4% of the 900 GB/s target.

CPU and DRAM behavior changed meaningfully with binding strategy, but NVLink did not. The data points to a persistent GPU fabric issue rather than a NUMA placement issue.

Findings

  • NVLink is independent of the tested NUMA policy in this dataset. The failed metric varies by less than 0.2 GB/s across all successful runs.
  • Binding only CPU execution to node 0 produced the highest observed 4 proc x 52 threads CPU FP32 best result, but the median stayed much lower. That looks like instability rather than durable improvement.
  • Binding memory to node 0 without CPU binding gave the most balanced valid run: strong DRAM bandwidth, no invalid configuration, no extra summary-path anomaly, and normal GPU metrics.
  • Binding both CPU and memory to node 0 reduced multi-thread STREAM bandwidth relative to the unbound and memory-only runs.
  • The invalid membind=1 command confirms this environment does not expose NUMA node 1 for binding.
Focus on NVLink rather than NUMA policy if the goal is to isolate the persistent platform issue. None of the valid binding combinations changed the NVLink result enough to matter.

Recommended Interpretation

If the goal is to isolate the persistent platform issue, focus on NVLink rather than NUMA policy. None of the valid binding combinations changed the NVLink result enough to matter, and every successful run failed at nearly the same threshold gap.

If the goal is to choose a stable comparison mode for future CPU-side measurements, numactl --membind=0 is the least noisy of the tested variants. numactl --cpunodebind=0 alone produced the most dramatic CPU headline number, but it also showed the clearest instability and one anomalous end-to-end PCIe regression.

Recommended Follow-up

  1. Validate actual NUMA topology with numactl --hardware before trying additional node combinations.
  2. Re-run the dedicated NVLink test repeatedly to confirm the low bandwidth is not transient.
  3. Cross-check NVLink topology and health with GPU fabric tooling, because the NUMA policy changes are not moving that metric.
  4. Use membind=0 as the default comparison mode if you need one stable CPU-side reference for additional experiments.
